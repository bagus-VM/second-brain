## One-line Summary
*US government standard for validating the security of cryptographic modules in hardware and software.*

## Core Intuition
If you're building an IoT device that handles US government data (or sells to any organization that does), your cryptographic implementation needs to be independently validated. FIPS 140 is that validation. It's not just 'use AES' — it's 'prove your AES implementation is correct, your keys are protected, and your module physically resists tampering.' For IoT, the challenge is fitting rigorous crypto validation onto resource-constrained devices.

## Formal Definition / Statement
FIPS 140 (Federal Information Processing Standard) is a US and Canadian government standard that specifies security requirements for cryptographic modules. FIPS 140-2 (2001) is being superseded by FIPS 140-3 (2019, aligned with ISO 19790).

Four security levels:
- **Level 1**: Basic security — correct algorithms, no specific physical security. Lowest bar.
- **Level 2**: Tamper-evidence — physical tamper-evidence coatings or seals, role-based authentication.
- **Level 3**: Tamper-resistant — physical tamper-resistance, identity-based authentication, key zeroization on tamper detection.
- **Level 4**: Tamper-active — Complete physical envelope, environmental failure protection (voltage, temperature).

Cryptographic modules include hardware (HSMs, TPMs), firmware, software, and hybrids. Testing is performed by accredited Cryptographic Module Testing Laboratories (CMTLs) under the Cryptographic Module Validation Program (CMVP).

## Key Properties / Complexity
- FIPS 140-2/3 validation is mandatory for US federal government procurement
- Validation can take 6–18 months and cost $50K–$500K+
- Each algorithm implementation must be separately validated (AES, SHA, RSA, etc.)
- Level 1 is achievable in software; Levels 3–4 typically require hardware
- IoT devices typically use FIPS-validated crypto libraries (e.g., mbedTLS, wolfSSL with FIPS builds)
- Certificate is version-specific — module updates require re-validation
- The CMVP maintains a public searchable database of validated modules

## Worked Example
An IoT sensor vendor wants to sell environmental monitors to a US federal building:
1. They select a FIPS 140-2 Level 1 validated TLS library (e.g., wolfCrypt FIPS)
2. The library handles AES-256-GCM encryption and SHA-256 hashing
3. The module is tested by a CMTL for algorithm correctness and key management
4. After passing, a FIPS certificate is issued and listed on the CMVP website
5. The vendor can now claim 'FIPS 140-2 Level 1 validated' in their product documentation
6. The federal procurement officer verifies the certificate on the NIST CMVP database

## Common Pitfalls
- **'FIPS compliant' ≠ 'FIPS validated'**: Many vendors claim 'FIPS compliance' meaning they use standard algorithms, but haven't actually been validated. Only 'FIPS validated' has legal standing.
- **Module boundary matters**: Only the specific module (library, chip) is validated, not the entire device. The device can still have vulnerabilities outside the module boundary.
- **Version lock**: Updating the crypto library invalidates the certificate. This creates tension with IoT security patching.
- **FIPS 140-3 transition**: New submissions must use FIPS 140-3, but many IoT products still reference 140-2 certificates.
