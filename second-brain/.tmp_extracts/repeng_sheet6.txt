2      Challenges in Reproducing Binary Builds
So far, we have worked primarily with interpreted programming languages such as Python.
In this exercise, we will focus on compiled binaries instead. Re-creating binaries from
source code might seem an easy task, but there are many factors that affect reproducibil-
ity. We discuss some of these factors using a simple C program as an example.

3      Reproducible Toolchains: Compiling Python
For some reproducible builds, building software from the source code is necessary, for
instance, because the binaries are not readily available or because some modifications to
the software are made. As an exercise, we build Python from source.
 (a) Inside the Docker container from Exercise 2, create a new directory named task3
     and enter it.
 (b) Download Python 3.12.3 from the official release server:

         user@container$ curl -O \
             "https://www.python.org/ftp/python/3.12.3/Python-3.12.3.tgz"


                                             3
 (c) Unpack the source code.

       user@container$ tar -xvf Python-3.12.3.tgz

 (d) Configure the build “out of source”.

       user@container$ mkdir build
       user@container$ cd build
       user@container$ ../Python-3.12.3/configure \
           --prefix=$HOME/Python-3.12.3-custom

 (e) Start the build process:

       user@container$ make -j $(nproc)

      Hints:
        • -j $(nproc) configures make to use all available cores on your system (if
          possible). This usually speeds up the build process but increases system load.
          To configure the number of parallel threads used in the build process, replace
          $(nproc) with the desired number.
        • Building Python will take a while. You can continue working on the next
          exercises while you wait.

  (f) Discuss why an “out of source” or “out of tree” build is considered good practice.


4     ReproTest
A central aspect in ensuring reproducible builds is testing them in different environments.
ReproTest is a tool that supports this process by building a program twice in different,
simulated environments, and checking whether identical binaries have been produced.
For this exercise, we will use a different Docker container.


4.1    Extending the Dockerfile

Stack
This is the section of memory used for local
variable storage. Every time you call a
function, all of the function’s local variables
get created on the stack. It’s called the stack
because it’s like a stack of plates: variables get
added to the stack when you enter a function,
and get taken off the stack when you leave.
Weird thing is, the stack actually works upside
down. It starts at the top of memory and
grows downward.

Heap
This is a section of memory we haven’t
really used yet. The heap is for dynamic
memory: pieces of data that get created
when the program is running and then hang
around a long time. You’ll see later in the
book how you’ll use the heap.

Globals
A global variable is a variable that lives
outside all of the functions and is visible to
all of them. Globals get created when the
program first runs, and you can update them
freely. But that’s unlike…

Constants
Constants are also created when the program
first runs, but they are stored in read-only
memory. Constants are things like string

literals that you will need when the program
is running, but you’ll never want them to
change.

Code
Finally, the code segment. A lot of operating
systems place the code right down in the
lowest memory addresses. The code segment
is also read-only. This is the part of the
memory where the actual assembled code
gets loaded.
